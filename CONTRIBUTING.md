# Contributing

Thanks for helping. The code is MIT; every result in `results/` is CC0.

The most useful contribution is a run on a device that has no result yet. See
[Contribute a run](README.md#contribute-a-run). Runs of the same device with a
different Vulkan driver (Qualcomm vs. Turnip, or a newer Mesa) are just as
useful: that is the comparison nobody has published.

## Setup

```bash
python3 -m unittest discover -s tests
python3 -m snapbench build-site --samples
python3 -m http.server --directory site 8000
```

No dependencies. Installing `jsonschema` (`pip install jsonschema`) enables
one extra test that checks the built-in validator against the reference
implementation.

## Common changes

**A new SoC.** Add the part number to `SOCS` in `snapbench/socs.py`, and its
Android board codename to `CODENAMES` if you know it. Leave the GPU or Hexagon
version as `None` rather than guessing; what the device reports always wins.

**A new driver fact.** If a Vulkan property explains performance, add its
`vulkaninfo` key to `VK_FIELDS` (or the extension to `VK_EXTENSIONS`) in
`snapbench/drivers.py`, surface it in `summarize_vulkan`, add it to
`$defs/vulkan_gpu` in the schema, and extend a fixture in `tests/fixtures`.
Real `vulkaninfo` output from a Snapdragon device makes the best fixture.
Please add one if you have it.

**Moving to a newer llama.cpp, or changing the matrix.** Update
`snapbench/matrix.py`: the release tag and commit, every bundle's sha256 (from
`gh api repos/ggml-org/llama.cpp/releases/tags/TAG --jq '.assets[] | "\(.name) \(.digest)"'`),
and bump `MATRIX_VERSION`. Results from different matrix versions are never
compared in one table. Re-check the llama-bench output against the parser
first: capture `llama-bench -o jsonl` and `--list-devices` from the new
release into `tests/fixtures` and run the tests.

**A schema change.** Additive, optional fields can go into v1. Anything that
renames, removes or changes the meaning of a field needs
`result-v2.schema.json`, and the page and validator must keep reading v1.

## Reviewing result pull requests

CI validates every file in `results/` against the schema and the acceptance
rules (`python3 -m snapbench validate --accept`). Before merging, also check
that:

- the device and SoC look plausible together,
- numbers are in a believable range for that SoC (a 10x outlier usually means
  thermal throttling, a power-saving mode, or a wrong thread count),
- `llama_cpp.sources` says `release`. `custom` builds are welcome but should
  say what was changed in `submitter.notes`.

Issue-form submissions can be turned into a results file with
`python3 -m snapbench import-issue NUMBER`, then committed in a PR.

## Rules

- Never edit someone else's numbers. If a result is wrong, remove it in a PR
  that explains why.
- Never put invented numbers in `results/`. Demo data goes in `samples/`,
  is generated by `tools/make_samples.py`, and is labelled as such.
- Keep the runner on the Python standard library. It has to work on a fresh
  Termux install.
